# 怎麼寫一個 pack

pack 是「**這類專案要檢查什麼**」的可重用知識，放在 `kit/rules/<類別>/<id>.md`。它會被 `/frontend-devkit/init compile` 展開進各專案的 `resolved.md`，變成 reviewer／developer 的判定依據。**因此 pack 寫錯，錯誤會複製到所有啟用它的專案**——這是一份審核依據，不是筆記。

## 1. 能寫與不能寫（主檔 §6.1 的可執行版）

**可以寫**
- 這類技術棧要檢查什麼（清單式、可逐條對照 diff）
- 常見地雷與誤用形態（例：把新版元件庫的屬性名用在舊版上）
- 寫法慣例與術語定義
- 「不得放寬什麼」的類別描述

**禁止寫（退件條件）**
1. **可執行指令列**：完整命令、旗標組合、執行方式（那些是 profile `## 指令` 的工作）。
2. **timeout、測試項數、error 數**：一律執行期量測（主檔 D7）。
3. **路徑與檔名**：包括「入口在 `src/util/xxx.js`」這種。pack 只能寫「入口取自 profile 的 `## 安全慣例` 欄」。
4. **本專案專屬判斷**：具體元件名、具體檔案行號、具體業務規則。
5. **未經真實專案驗證的假設**：可以建立 pack，但 `status` 必須寫 `未驗證`，且不可聲稱「通常都是這樣」。

### 關於「旗標」的界說（本輪裁決）

主檔 §6.1 禁止「具體指令」，但 reviewer 需要知道某些**選項名稱**危險（例如會自動改寫原始檔的修正旗標、會落地快照的更新旗標）。界說如下，避免曖昧：

- 允許：**單獨寫出選項名稱**並說明「為何不得用它」，句型固定為「不得帶 `<--flag>`（會 ⋯）」。
- 禁止：把選項包進完整指令（例：把整條執行命令與目標路徑一起寫進 pack）。
- 若某選項的危險性只在於它會**寫檔**，則該知識應改寫為「任何會落地檔案或改寫來源檔的執行方式，都不准在審核過程中使用」（屬主體／permission-spec 範疇），而不是在 pack 列清單。

### 與主檔 §6.4 的衝突裁決（老實記錄）

主檔 §6.4 曾寫 `security/vue-xss` 提供「本專案的清理入口、既有危險點位置」，但 §6.1 禁止 pack 寫路徑與檔名。兩者衝突，**以 §6.1 為準**：入口與位置屬 profile `## 安全慣例`，pack 只寫「如何查這類問題」的方法。此裁決已回寫進 pack 正文（見 `rules/security/vue-xss.md` 第 1 行說明），並列入主檔 §15 風險表的建議修正項。

## 2. 檔頭格式

```md
---
id: stack/vue2-nuxt2
title: Vue 2 / Nuxt 2 慣例
status: 已驗證
source: 既有專案現有 reviewer.md／developer.md 逐條抽出（附檔 migration-map.md 有來源對照）
covers: options API 寫法、元件庫版本屬性誤用、目錄與載入慣例、程式風格
---
```

- `status` 只能是 `已驗證` 或 `未驗證` 兩個字面值。**不可加方括號**：方括號在 YAML 是 flow sequence，`[未驗證]` 會被解析成陣列。
- `covers` 一行自由文字，是 `compile` 做「主題重疊警告」的依據，也是別人決定要不要啟用的唯一資訊。
- 不設 `sections` 之類欄位：欄位級衝突無法機械偵測（主檔 §6.2），靠 `covers` 警告＋本節退件紀律。

## 3. 內文結構建議（不拘，但要有這四類）

1. **檢查清單**：reviewer 能逐條對 diff 打勾的問句。
2. **地雷**：誤用形態與判別線索（看什麼知道踩到了）。
3. **寫法慣例**：developer 該照什麼寫，含「為什麼」。
4. **不得放寬**：清單式（例：既有白名單範圍、既有退回路徑），並註明「放寬要在 profile 的 `## 專案覆寫` 寫理由，且安全檢查項只能覆寫成更嚴」（主檔 §3 第 3 點）。

## 4. 退件清單（review 時逐條打勾）

| # | 檢查 | 不通就退 |
|---|---|---|
| 1 | 檔頭五欄齊全，`status` 是兩個字面值之一、無方括號 | ☐ |
| 2 | 全文無完整指令列、無 timeout、無測試項數／error 數 | ☐ |
| 3 | 全文無路徑與檔名（用 grep 找 `/`、`.vue`、`.js`、`src/` 這類訊號，逐一判斷是否為專案專屬位置） | ☐ |
| 4 | 每個斷言都能追溯到「哪個真實專案的哪個現象」；無來源者必標 `未驗證` | ☐ |
| 5 | 與現有 pack 的 `covers` 是否有交集；有則說明為何不合併，或調整 `covers` 措辭（措辭避重不算解決，要真分派主題） | ☐ |
| 6 | 不重複主體 §3 第 0 點的通用危險模式（重複會造成同一發現被列兩次） | ☐ |
| 7 | 繁體中文、代碼塊標語法、無殘留錯字（跑 `tools/normalize-forms.ps1` 後**人工重讀受影響行**） | ☐ |

## 5. 落地步驟

1. 在 `kit/rules/<類別>/<id>.md` 寫 pack；`<類別>` 用 `stack`／`testing`／`security`／`i18n`／`style`。
2. 在 `kit/rules/registry.md` 補一列（含 `covers` 與「適用偵測訊號」）。
3. 找一個真實專案啟用它，跑 `/frontend-devkit/init compile`，確認 `resolved.md` 展開正確。
4. 該專案走過一次完整 dev／review 流程後，才把 `status` 從 `未驗證` 改成 `已驗證`（改動要附是哪個專案、哪次任務）。
5. 升級 pack 後，所有啟用它的專案都要重跑 `compile`（README 的固定步驟）。
