本 pack 管「這類專案要檢查什麼」，**不管指令、路徑與數字**（那些在專案 `project.md`）。

## 檢查清單（reviewer 逐條對 diff 打勾）

1. 元件是否維持 **options API** 一貫風格；同檔混用 composition API 寫法要提出來（除非該專案 profile 明說可混用）。
2. 元件庫属性是否為**該大版本存在的属性**：Vuetify 1 的元件與属性名與 2 不同，常見誤用是把新版屬性、新版組件寫法（例如表單、彈窗、栅格相關的 2.x 屬性名）貼到 1.x 上——這類錯誤在編譯期不一定報錯，執行期才靜默失效，屬**一般**起跳、造成功能壞掉則**嚴重**。
3. 生命週期與渲染時機：服務端／用戶端差異的處理是否沿用專案既有模式（Nuxt 2 的客戶端專用掛載、動態匯入需關聯到該專案的目錄慣例）。
4. 全域註冊的元件／插件是否被重複區域註冊（同一名稱兩處註冊會造成難以追蹤的覆蓋行為）。
5. 命名與結構是否符合該專案既有慣例（看 profile `## 回歸熱點` 與目錄慣例，不另立標準）。
6. 樣式是否走專案既有方式（全域樣式檔的 class／選擇器改動要做使用處分析；優先新增專屬 class，而非改共用規則）。
7. 風格一致性：遵循該專案的 lint 規則集（**不在 pack 指定規則內容**；只要求「與周圍程式碼一致」，具體 gate 由 profile 的 lint 條目決定）。

## 地雷（看到這些線索就深查）

- 屬性名前綴換代風格式（新版命名習慣出現在舊版元件上）。
- 用新版網格／佈局元件概念改舊版版面。
- 把元件的雙向綁定寫成新版的修飾符語法。
- 以全域事件總線或 refs 跨層通訊，取代 props／events（造成影響範圍超出檔案本身，回歸分析易漏）。
- 把整個共用元件當成「只改一個小屬性」的局部改動，實際它是多處接線的節點——必須回到 profile `## 共用項目類別` 做使用處分析。

## 寫法慣例（developer 依此實作）

- 先讀同目錄／同類別的既有元件再動手，風格跟隨周圍程式碼，不順手重構無關部分。
- 新增依賴前先看既有依賴能否勝任（**不新增不必要的依賴**是主體紀律，本 pack 只補充：此類專案的生態版本耦合緊，升級間接依賴容易連動壞掉）。
- 對外觀感變更（樣式、版面）要同時考慮桌面與手機斷點——這是本類別專案最容易在自動化裡漏掉的部分，需進入「建議手動回歸檢查」。

## 不得放寬

- 既有元件的 props／events／slot 名稱與預設值：改名或刪除需所有使用處同步，且需在 profile 留理由（主檔 §3 第 3 點）。
- 既有 lint 規則集的嚴格度；「關掉規則讓它過」屬削弱檢查，一律列問題。
