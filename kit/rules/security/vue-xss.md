**通用危險模式清單在主體（主檔 §3 第 0 點），本 pack 不重複列舉**；本 pack 只補「Vue 型專案要怎麼把這類問題查實」的方法，以及哪些放寬是不可接受的。清理器的**實際入口、白名單內容、既有危險點位置**一律取自專案 `project.md` 的 `## 安全慣例`（依 `docs/writing-a-pack.md` 的裁決，本檔不寫路徑也不寫檔名）。

## 檢查清單

1. **綁定回溯**：每個插入原始 HTML 的綁定（模板指令或 DOM 屬性兩種形式）都要回溯到資料來源：使用者輸入、即時通訊推送、API 回應、網址參數、還是編譯期就固定的靜態文字。只有「編譯期靜態且不可被外部影響」才算安全。
2. **清理時點**：清理必須發生在**渲染之前**的那條路上。**只在送出端清理不算數**——送出端清理只保證寫入時乾淨，顯示路徑仍可能接到別來源（後端歷史資料、他人建立的資料、跨頁面參數）。
3. **中間轉換層要查**：資料到渲染之間若有 markdown 渲染、模板編譯、字串拼接、HTML 片段組合，要確認轉換層**不會過過**清理；最常見的破口是「直接放轉換結果」而轉換器被關掉淨化選項。
4. **白名單範圍**：淨化器的標籤／屬性／協定白名單被擴充時，要逐項問「誰需要它」。重點看四類：可載入外部資源的標籤、樣式相關屬性、事件相關屬性、非 http／https／mailto 的協定。縮小範圍一律放行，擴大範圍需要 profile 的理由。
5. **動態協定與跳轉**：位址、資源來源、視窗開啟、導向賦值的動態值，是否可能被帶入非預設協定（含「省略協定的相對協定寫法」、「大小寫混雜」、「前置空白」這規避形態）。
6. **退回路徑**：當淨化器不可用時是否有退回方案（例如轉義成純文字）。**「淨化失敗就放原始字串」是嚴重問題**，正確退回是 fail-closed（不渲染或轉義）。
7. **專案覆寫的界**：profile 可以加嚴（例如多一層白名單、多一個檢查點），**不可以**取消或降級本 pack 與主體第 0 點的任一檢查（主檔 §3 第 3 點例外一）。Reviewer 遇到此類覆寫：照樣查，引用該覆寫原文，列「嚴重」。

## 地雷（常見把安全做法誤以為有效的形態）

- 只擋 `<script>`，留其他可執行向量（事件屬性、可載入外部資源的標籤、協定型屬性）。
- 用「移除某些字串」代替白名單式淨化（黑名單幾乎一定能被過過）。
- 把外部內容當成「自家後端送的，所以可信」——後端內容同樣可能帶使用者原文（使用者輸入、第三方資料、歷史資料）。
- 清理只覆蓋文字內容，未覆蓋屬性值與 URL 型屬性。
- 透過插槽、動態元件、模板字串把內容塞進去，過過原本有淨化的那條路。

## 寫法慣例（developer）

- 新渲染路徑預設走「先清理再渲染」，並在程式碼旁註明清理點，方便 reviewer 回溯。
- 需要富內容呈現時，優先擴充既有白名單的**保守子集**，而不是全域放行；每次放寬都要能說出用途。
- 敏感資料（憑證、個資）不得落到瀏覽器端長期儲存、記錄輸出或網址參數——這是主體第 0 點的通用項，Vue 專案的常見落地位置是狀態管理層與本地儲存包裝層，查 diff 時特別看這兩處。

## 不得放寬

- 渲染前清理的要求、白名單的既有範圍、淨化失敗的 fail-closed 行為。
- 「既有危險點清單」（專案 profile 裡記錄的那些位置）只能變短不能變長：新增了插入原始 HTML 的位置，就是要新加入清單，並說明它的來源與清理點。
